# Harness coverage record: features -> scenarios

Which of spec #28's features have a scripted AFK-harness scenario proving them. Updated by each
sub-issue as it lands (#29-#46). See `docs/dev-setup.md` for how to run the harness and
`decomp-so/reference/coverage.md` for the *reconstruction's* function-level coverage (a different,
earlier record from spec #16 - that one tracks decompiled functions against reference files; this
one tracks spec #28 features against harness scenarios).

- **Status:** `covered` = a scripted scenario in `tools/` (or a documented harness invocation)
  exercises the feature and the harness's checks pass (or, for #29 only, are expected to report
  red - see its row). `pending` = no scenario yet.
- **Scenario** names the harness entry point that exercises the feature.

| Objectives (`mkObjective`) + `idPlayer::addObjective`/`freeObjective`/`addItemText` | `tools/test-objectives.sh`, `tools/test-item-text.sh` | covered - loads `sf_923` (the only map with `trigger_objective` entities) and triggers both `trigger_objective_1` and `trigger_objective_2`: triggering fills `chextrek_dump`'s `objective_slot_N` with the objective's title, a second trigger on `trigger_objective_1` empties its slot without disturbing `trigger_objective_2`'s, and a `savegame`/`loadgame` round-trip leaves `trigger_objective_2` (the only one still active going into the save) attached and shown in the dump. `idPlayer::HudMapLevel`, which `addObjective` calls to fill `mkObjective::mapLevel`, is a stub returning 0 (`Player.cpp`) - its real body (`decomp-so/reference/hud-map.md`) needs `idPlayer::mapLevels[]` and the rest of the HUD map group's members, not yet ported (see the "HUD map" row below); nothing yet reads `mapLevel`, so the stub is inert. **Confirmed live, not just inferred from the reference:** after a save/load, a lone active objective can come back in a *different* slot than it had before saving (`trigger_objective_2` came back as `objective_slot_1`, not `_2`) - `decomp-so/reference/objectives.md`'s Notes call this out as an open question (`nextObjective` isn't saved, and it's the reconstructed `idPlayer`'s *constructor* that zeroes it back to 0 on the reload - `idPlayer::Restore` never calls `Init()` - so re-attachment order, not original slot, decides the new slot). This is the reconstructed mod's actual behavior, not a harness bug or a regression to fix (spec #28 targets original behavior, not enhancements), so the scenario asserts the exact, deterministic post-load slot (`objective_slot_1`) this produces here, rather than treating the renumbering as untestable. A second `savegame`/`loadgame` immediately after (from that already-in-slot-1 state, where the objective is already sitting in the first free slot) checks the literal wording of the acceptance criterion too: that round-trip leaves `objective_slot_1`/`_2` unchanged, the "same objective slots" case. **`addItemText` (spec #32):** now separately asserted by `tools/test-item-text.sh`, not just exercised as a side effect. `addItemText`'s only callers in the reconstructed binary are `mkObjective::AttachToLocalPlayer`/`RemoveFromLocalPlayer` (`decomp-so/reference/objectives.md`'s Notes), so "picking up an item [that] shows its item text" means picking up an item that targets a `trigger_objective`. `maps/sf_923.map`'s own `moveable_item_pistol_1` (`target1` `trigger_objective_1`) is that item - but `trigger_objective_1` is itself first triggered by `trigger_once_6` (`target3`, along with `trigger_objective_2` via `target4`) earlier in a real playthrough, which *attaches* both objectives (`addmsg` "New Objective" each); the pistol pickup is `trigger_objective_1`'s *second* trigger, which *removes* it (`rmmsg` "Objective Complete") rather than showing "New Objective" again. The scenario reproduces both triggers in that order so the item text it asserts after the pickup ("Objective Complete") matches what an actual playthrough would show, not an order the map never produces. Because `idPlayer::UpdateHud` drains `inventory.pickupItemNames` into HUD GUI state within a frame or two of `addItemText` filling it, the queue itself isn't reliably observable from a scenario's `chextrek_dump` (which runs after a `wait`); a test-only hook (`ChexTrek_NoteItemTextShown`, called from `addItemText` itself, `Player.cpp`, the same "hook added to already-ported game code" pattern as spec #30's `ChexTrek_NoteFootprintProjected`) records a call count and the last name *queued*, printed as `chextrek_dump`'s `item_text_count`/`item_text_last` lines. This proves `addItemText` ran with the expected name (spec #32's AC), not that `UpdateHud` went on to render it on screen - `decomp-so/reference/objectives.md`'s Notes flag that render path (`hud.gui`'s commented-out `invPickup`/`itemicon` wiring) as not checked. |
| Custom UI (`idCustomUI`) + end-level stats (`idTarget_EndLevelGUI`), incl. stat counting | `tools/test-end-level-stats.sh` | covered - `idCustomUI` (`decomp-so/reference/custom-ui.md`) and `idTarget_EndLevelGUI` (`decomp-so/reference/end-level-stats.md`) ported in full, including `idPlayer::useCustomUI`/`clearCustomUI`/`incSecretsFound`/`getLevelStats`/`levelStats[4]`, `idGameLocal::GetLevelStats` and `idStr::FormatTime`. **Out of scope, not needed by #33's AC:** the `g_PDA` cvar and `idCmdSystem::ArgCompletion_GuiName` that `custom-ui.md` bundles into the same Ghidra export group - their only registration site is the PDA GUI file (spec #28 story 19, a separate feature the reference's own Notes say doesn't belong to this group functionally), not anything `idTarget_EndLevelGUI` reads. Scenario: on `e1m1`, spawns a monster and radius-damages it with the player as attacker (`sys.radiusDamage`, since the `kill` script event credits the AI itself, not the player - `idAI::Event_Kill` - and wouldn't exercise the edit-inside-`AddAIKill` lead), spawns and picks up a fresh `ammo_bullets_small` (not one of `e1m1`'s own placed items - a health-only item's `idPlayer::GiveItem` silently no-ops when the player is already at full health, which the reference's `gave` check means never counts as a pickup either), and triggers a `secret`-flagged `func_door_16`: `chextrek_dump`'s new `level_stats: monsters=<found>/<total> items=<found>/<total> secrets=<found>/<total>` line rises by exactly one across each action. Then triggers `target_endlevelgui_1` (`g_statTicTime` set to 1 first so the counting animation catches up in well under a second instead of the default ~50ms/tic pacing) and confirms the dump's new `customui: none -> active` line plus `customui_gui_ai_killed`/`items_found`/`secrets_found` (read from the GUI's own state, `idUserInterface::State()`) match `level_stats`. A second, shorter run loads `sf_923` and triggers its own `target_endlevelgui_1` the same way, covering the AC's "both maps" requirement for the half `e1m1`'s run doesn't reach. **Edits-inside-stock-functions leads recorded for #33** (not in the #16 export, since `idMover_Binary::Use_BinaryMover` and `idPlayer::GiveItem(idItem*)` are stock, pre-existing functions, same pattern as #30-#32's leads). Both are **checked against the `gamex86.so` disassembly** using `decomp-so/verify`'s own tooling (`capstone`/`pyelftools`, already listed in its `requirements.txt`): `idPlayer::GiveItem(idItem*)` increments `levelStats[1].found` only when it both actually gave something (`gave == true`) *and* the picked-up item's own `spawnArgs` has `"level_item" "1"` (`idPlayer::GiveItem` @ 0x164cd0; the guarding `FindKey`/`atoi` sequence at 0x164f1d-0x164f64 resolves to the rodata string `"level_item"` - the same key `idGameLocal::GetLevelStats` counts into `levelStats[1].total`); the secret counter is credited by two of `idMover_Binary`'s own new members, `secret` (mirrors the `"secret"` spawnArg, set once in `Spawn`, disassembly 0x1384e5) and `secretFound` (guards against double-crediting; both zeroed in the constructor, 0x132f78/0x132f7f), checked at the very top of `Use_BinaryMover` (0x136c70) - before even the "only the master should be used" redirect, so it runs at every level of a moveMaster chain via that redirect's recursion - and skipped entirely in multiplayer (`gameLocal.isMultiplayer`). `idPlayer::AddAIKill` increments `levelStats[0].found` unconditionally, before its existing soul-cube-ammo early return; this one matches the reference's own cited address (0x15e878) and wasn't separately re-checked against the disassembly here. **Open lead, not confirmed:** whether the binary's own `idMover_Binary::Save`/`Restore` persist `secret`/`secretFound` - this port saves/restores both anyway (so a save/load round-trip can't re-credit an already-found secret), a deliberate, documented departure if the binary doesn't. |
| Stats-screen `nextmap`/`skip` commands (`idTarget_EndLevelGUI::HandleCustomGUICommand`, spec #28 story 18) | `tools/test-end-level-nextmap.sh` | covered - the method itself was already ported in full by #33 (`Target.cpp`); #34 is scenario coverage proving its two GUI commands actually work as `decomp-so/reference/end-level-stats.md` describes them. Both commands only ever reach the game, in the real game, through a mouse click on `guis/chex/stats.gui`'s `skip`/`nextmap` buttons (`onAction` -> `idPlayer::Weapon_GUI`'s `BUTTON_ATTACK` handling -> engine-side `idUserInterface::HandleEvent`), which needs real mouse-delta input (`usercmd_t::mx`/`my`) the console-only harness (`map`, `script`, `setviewpos`, `trigger`, `spawn`, `impulse`, `wait`) can't produce. **New test-only console command, `chextrek_customui_cmd <command>`** (`ChexTrekDump.cpp`/`.h`, registered in `gamesys/SysCmds.cpp`) closes that gap the same way the state-dump command closes its own: it reads one token the same way `idPlayer::HandleSingleGuiCommand` would and passes it to the local player's registered `idCustomUI` through the exact same virtual call a real click reaches (`HandleCustomGUICommand`) - everything downstream is the already-ported #33 code, unchanged; the command itself changes no game behavior beyond what a click would have produced. Scenario: on `e1m1`, reuses #33's kill/pickup/secret setup so `level_stats` isn't trivially 0/0, triggers `target_endlevelgui_1`, waits just long enough (10 frames, comfortably above the one default-paced `g_statTicTime` tic needed to flip the screen's internal state from "not started" to counting the first line, comfortably below the ~4 tics needed to finish that first line on its own - see the script's own header comment for why a `g_statTicTime` override was tried and abandoned) for the screen to have started but not finished counting, then sends `chextrek_customui_cmd skip` four times back to back (no `wait` between, so no naturally-scheduled tic can interleave): each jumps the current line (monsters, items, secrets, then the level-time line) straight to its final value, checked against `chextrek_dump`'s `level_stats`/`customui_gui_*` lines rather than a hardcoded number. A guard assertion (dump #3's `ai_percent`, before any `skip`, strictly below the final target) catches the one failure mode a bad wait could cause: natural counting finishing the monsters line before the scenario's own `skip` calls start, which would silently shift every later `skip` onto the wrong line while still reporting "handled". On `sf_923`, `idTarget_EndLevelGUI`'s "nextmap" GUI command is *not* how the shipped map actually reaches `e1m1`: neither of its own `target_endlevelgui` entities has a `nextmap` spawnArg (Notes: "set on no `target_endlevelgui` in `maps/`"), and the map's real `"nextMap" "e1m1"` key (`maps/sf_923.map:35106`) lives on `target_endlevel_3`, a stock `idTarget_EndLevel` reached only via a separate script (`script/map_storage_facility.script`) off `target_endlevelgui_2`'s `end_trek.gui` - none of that chain is `idTarget_EndLevelGUI::HandleCustomGUICommand` or anything #33/#34 ported, and driving it is out of scope here. Since no shipped map ever gives `idTarget_EndLevelGUI`'s own `nextmap` spawnArg a value, the scenario spawns a fresh entity that does (`nextmap` `e1m1`; `spawn` supports extra key/value pairs, same as any other spawnclass) - the only way to exercise that specific, ported mechanism at all, and a direct reading of AC2's literal wording ("nextmap ... loads e1m1"). Triggers it, sends `chextrek_customui_cmd nextmap` (no state guard on this command, so it works even before the first tic), confirms the log actually shows `chextrek_customui_cmd: 'nextmap' handled` (so a later, coincidental map load can't pass this on its own), and confirms `e1m1` finishes loading next - the same `"<N> msec to load <map>"` evidence every other map-load assertion in this table already uses. **Recorded deviation from spec #28's Implementation Decisions** (which describe the state-dump command as "the only test code in the library"): `chextrek_customui_cmd` is a second test-only console command, needed because nothing in spec #28's console-only command list can simulate the mouse click these two GUI commands otherwise require - the same class of gap the state-dump command exists to close, on the driving side rather than the observing side. Gated `CMD_FL_CHEAT` plus its own `CheatsOk( false )` check, matching `Cmd_Trigger_f`/`Cmd_Spawn_f` - honestly weaker than "developer-only" (spec #28 story 34, which the state-dump command matches): `CMD_FL_CHEAT`/`CheatsOk()` only block non-cheat multiplayer clients, not single-player without `developer 1` (an explicit `developer.GetBool()` check was tried and reverted after it broke the harness scenario for an untracked reason). Narrower in practice, though not in principle (multiplayer with `net_allowCheats 1` still passes the gate): the command can only change anything when a player-triggered `idCustomUI` is already registered. |
